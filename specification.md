# Quorum specification

## Current scope

Quorum is a browser-based daily knowledge and optimisation puzzle. The first iteration is entirely client-side: no API, database, authentication service, remote analytics or live fact lookup is involved. Cloudflare Workers can serve the static build. Client-side facts and answers are inspectable; results are for local playtesting, not authoritative competition.

## Gameplay

Each unstarted day opens on a welcome screen with a brief Choose / Check / Refine summary, previous/next links to browse available puzzles, and a prominent “Let’s Play” button as its primary action. Countries and requirements stay hidden until play starts. During playtesting, a 5-minute timer switch is available here on all hosts, including preview deployments, and defaults to on. The choice is fixed for that run; returning to an active or finished day resumes it directly. Existing saved games with selections or checks resume untimed.

Each puzzle presents twelve countries and six requirements. Players select one to six countries and submit up to three checks. A selection meets a requirement if at least one selected country has a verified true relationship with it. A country can meet several requirements; multiple countries meeting one requirement do not increase coverage.

Selection alone reveals no coverage in the daily fixtures. Cards display a flag and country name, without continent or regional clues. After a check, the requirement list marks covered and missing requirements, with a count and attempt history. Changing cards keeps the previous check’s feedback visible, with a caption identifying it as coverage from the last check. Rechecking an identical combination, regardless of order, is rejected without spending a check.

A complete result ranks ahead of an incomplete result. Complete results rank by fewest countries; incomplete results rank by most requirements covered, then fewest countries. Ties keep the earliest check. A later failed check cannot replace a complete result. Three countries is a Perfect Quorum; four to six is a Complete Quorum. An unchecked selection never counts as a result.

In timed mode, pressing “Let’s Play” saves a start time and a deadline five minutes later. A visible countdown warns during the final minute. Time continues through dialogs, refreshes, navigation to another day and time away from the page. Reaching zero automatically ends play and reveals the best checked result, including an incomplete result if no checks were used. Unchecked selections are not automatically submitted. Expired games reject further checks even before the next display update. Untimed mode has no deadline. Shared timed results are labelled “5-minute mode”.

The third check ends play automatically. Players may finish early, including without checking, after confirming that this reveals the answers and ends the run. The result shows the best checked selection, checks used, one optimal solution, the number of optimal combinations, and expandable factual explanations with sources. All candidate relationships can be explored after completion. A spoiler-free text result includes the date, puzzle number, score, coverage progression and game URL. Sharing tries native sharing, then clipboard, then a manually copyable text area.

The daily boards combine cultural heritage, sporting history, economic and population comparisons, density, size and estimated capital distances. Each board mixes at least three subject categories, at most two questions per family, and one or two estimation questions across all comparison and distance formats combined, with editorial easy, medium and hard questions. Each board also mixes country familiarity bands. These authoring labels are not displayed during play and require playtesting to calibrate. The specific autocracy-in-1980 question is not used in the daily collection.

Each board has an authored conservative selection of five or six countries that covers everything and loses coverage if any member is removed. Reaching three requires replacing countries to exploit overlaps, rather than simply pruning that selection. Only one to four of the 220 possible triples solve each current board. Other complete combinations exist at four, five and six countries, including four-country solutions containing no optimal triple. This constrains the available routes; it does not predict the distribution of player scores.

## Daily schedule and testing

`src/content/puzzles.json` defines the UTC epoch (22 October 2026) and seven ordered, reviewed puzzle definitions produced by the offline generator. The UTC day offset determines the puzzle number and selects a fixture by cycling through this collection. Everyone using the same content build receives the same fixture on the same UTC date. Content repeats every seven days with separate dated progress; this is a testing schedule, not an unlimited daily puzzle generator. Without an explicit date, open tabs switch days at the next 15-second check or visibility change.

Previous and next arrows flank the header’s puzzle number on every hostname. They browse the seven-day block containing the selected date, aligned to the epoch, wrapping at either end. They use ordinary `?date=YYYY-MM-DD` links, so refresh, sharing and browser history retain the selected day. A valid explicit date pins that day instead of rolling over at midnight. Invalid dates fall back to today. The Quorum logo returns to the unpinned daily game. Each date retains its own start time, optional timer deadline, selection, checks and completion, including when the same fixture repeats a week later. Shared results always link to their explicit date.

On localhost, a testing icon additionally opens a dialog with a date preview, a reset for that day’s run and an event export. These extra controls are not shown on deployed hosts. Dates before the epoch remain supported as backwards test fixtures and can have non-positive puzzle numbers.

## Interface

The interface uses a restrained paper, forest-green and sage palette, system sans-serif controls, Georgia display text and native flag emoji. All assets are local; external source links open only when requested. Countries precede requirements in the document. Wide screens place a three-column country grid beside a single list of requirements. Portrait phones place a four-column country grid above six full-width requirement rows, with a fixed bottom bar for selection count, Clear, remaining checks, Finish & reveal and Check selection. Landscape phones place countries beside the requirement list. The header shows the Quorum wordmark with the date and puzzle number beneath it. A prominent sans serif instruction asks “How few countries can tick every box?”. Requirements use one line-separated checklist on every screen size. Puzzle titles, theme labels, the country section heading, initial helper copy and promotional footer text are omitted; country and requirement regions retain accessible names. Coverage feedback and selection errors appear when relevant. Country tiles and requirement rows grow with the available viewport height, retaining compact sizes on short screens. Compact spacing keeps the playable board within common phone screen proportions, including space lost to browser controls. History, detailed feedback and results can scroll below the board; enlarged text or unusually short windows can also scroll rather than clip content.

Country tiles have touch targets at least 44 pixels high. Each requirement has an empty square box; a covered requirement gains a tick and green row highlighting after a check. Uncovered boxes remain empty. Coverage is included in accessible labels rather than visible Met/Missing text. The boxes indicate check feedback; clicking a requirement opens its definition. Buttons support keyboard input and visible focus; native dialogs handle focus containment and Escape. Reduced-motion preferences disable reveal animations.

The header help button opens How to play, including an interactive two-island example independent of the real puzzle. Help is available before starting and during play; it does not pause a running timer.

## Content and enrichment

`src/content/countries.json` contains thirty-two countries, thirty-four reusable requirements, display metadata, a content version, review date, explicit scope and a source registry. All countries have dated 2023 World Bank population, total nominal GDP and surface area observations, fixed capital coordinates, and reviewed continent, equator, hemisphere, landlocked and euro facts. Some other manual facts remain reviewed only for the original twelve countries. Available political regime observations cover 1980 and 2024; Germany’s missing 1980 observation remains unknown because the source separates East and West Germany. Sources record retrieval dates and data licences where applicable. Requirements have an editorial question family, reasoning type (recall or estimation), subject category and difficulty; countries have an editorial familiarity band. These labels guide authoring rather than factual answers or scoring. Political observations remain available but the specific 1980 question is disabled for publication with `generationEnabled: false`.

Requirements may use a manual fact or one of five structured rule formats: compare a metric with a reference country; measure capital distance from a named city; compare distances to two cities; match a dated event in a reviewed collection; or match a political regime classification in a specified year. The metric comparison format also derives GDP per person and population per total surface area. `src/content/requirements.ts` resolves these rules against the fixed local observations, producing the same `value` (true, false or null), `explanation` and `sourceIds` matrix consumed by the existing engine. Generated explanations include actual figures, distances or historical records. Numeric comparisons use unrounded values from the same year. Great-circle distances use fixed city points and an inclusive distance limit; “closer” comparisons are strict. Capital conventions use Jakarta for Indonesia, Pretoria for South Africa and Sucre (the constitutional capital) for Bolivia, as stated in definitions.

Event collections contain a reviewed date interval, an explicit list of reviewed countries, source references and dated records. The six collections cover main Summer and Winter Olympic hosts through 2024, men’s World Cup winners through 2022, women’s World Cup winners through 2023, and named participants in UNESCO’s Mediterranean diet and Tango inscriptions through 2024. An absent event means false only when the country and entire requested interval were reviewed. Political history uses V-Dem v16’s Regimes of the World, processed by Our World in Data; “autocratic rule in 1980” means a closed or electoral autocracy in that specific year. These are pinned content snapshots, with no runtime ingestion, external requests or moving “latest” dates.

Missing or null means unknown; it never means false. New countries’ unreviewed manual facts remain unknown. Every published candidate/requirement pair must resolve to an explicit boolean, non-empty explanation and recognised source reference. The loader rejects incomplete boards. Comparison reference countries are automatically ineligible for a board using that comparison; optional `excludedEntityIds` on any requirement adds editorial exclusions. Exclusion is separate from factual truth, and unresolved exclusion references are errors.

Geographical requirements use primary territory (including integral islands), excluding overseas regions and dependencies; France means metropolitan France. Transcontinental countries can cover multiple continents: Egypt covers both Africa and Asia because Sinai is in Asia. Definitions are available during play without revealing individual relationships. Language means national official status; euro means official national currency; Atlantic includes the Gulf of Guinea but excludes the Mediterranean.

To enrich content without changing engine code:

1. Add source records with stable IDs, titles, URLs and retrieval/version information. Verify facts against the stated definition and retain attribution and applicable data licences.
2. Add attributes with stable IDs, labels, precise definitions, a subject category, family, reasoning type and editorial difficulty. Either add reviewed manual relationships or configure an existing rule format. New instances need JSON edits; a new rule format requires compiler code. Keep definitions consistent with parameters and family classifications.
3. Add countries with an ID, name, flag, editorial familiarity and any needed observations and reviewed manual facts. Explicitly review event collection coverage before adding a country to its reviewed list. Unreviewed relationships remain unknown. Regional `clue` metadata is retained but hidden on tiles. Extra countries need not appear in every puzzle.
4. Generate proposals with `npm run puzzles:generate`, or edit definitions manually. Definitions reference country and attribute IDs; rules configure selection/check limits, intended optimum and clue mode. `authoring.safeSelectionIds` stores a conservative route for audit, without affecting scoring. Hidden and partial modes show flags and names; full mode also lists matching requirements for explicit clue-based fixtures.
5. Inspect reports, review sources and playtest before replacing `puzzles.json`. Run `npm run puzzles:audit` and `npm run check`. Bump a puzzle version when changing a previously used ID’s rules/candidate/requirement set, and the catalog version when facts change. There is no complete historical content archive.

Flags use native emoji. New themes can use the same catalog/puzzle shapes, but registering another theme file requires a loader change. Abstract-symbol fixtures already exercise the engine in tests.

## Puzzle quality and offline generation

`quality-profile.json` holds the active, versioned publication policy. `quality.ts` applies it to exact solver measurements, separately from gameplay rules. It checks candidate/requirement counts, family and combined estimation caps, subject/difficulty/familiarity mixes, useful countries, matching-country frequency, optimum size/count, completion-rate bands, irreducible routes and requirement implications. The current profile allows one to four optimal triples, requires irreducible fours and fives plus a conservative five/six, and prevents a question’s answer set from being a subset of another’s. Completion rate is the fraction of all country combinations of that size that cover every requirement. These are structural proxies, not predictions of player scores. Familiarity and difficulty are editorial estimates requiring playtest calibration.

`audit.ts` applies the same policy to authored or generated definitions, verifies each stored conservative route and declared optimum, and checks unique IDs/question sets plus adjacent-day question overlap (including the looping schedule boundary). The current overlap limit is four questions. Publication content tests run this audit before builds.

`generator.ts` is a bounded, deterministic authoring search over the resolved catalog. Each attempt samples a recall/estimation question mix, checks metadata variety and schedule overlap, excludes prohibited or unverified countries, proposes an irreducible conservative route using private requirements, fills the remaining country slots, checks familiarity, and sends the board to the exact solver and shared assessor. It greedily keeps accepted boards until the requested count or attempt budget is reached. Failed proposals do not establish impossibility. The generator never relaxes constraints, performs no live ingestion and does not run during play.

`npm run puzzles:generate` accepts seed/count/attempt/trace settings, an optional profile file, and optional candidate/report paths. `npm run puzzles:audit` audits the current or specified schedule, optionally writing reports. Reports expose active settings, exclusions, quality failures, exact solution counts, irreducible/prunable routes, answer matrices and schedule coverage; generation also records algorithm/catalog/profile versions, seed, attempt totals, rejection counts and bounded detailed traces. JSON is machine-readable and a Markdown companion is human-readable. Exhausted generation returns partial results with a failing exit status, never silently weakening a constraint. There is no default publication side effect. Detailed commands and the algorithm are documented in `docs/puzzle-authoring.md`; `docs/puzzle-quality-report.md` and its JSON companion record the current generated week.

## Rules, validation and architecture

The React/TypeScript interface is built by Vite. `src/game` contains framework-independent types, coverage calculation, ranking, check limits, sharing text and exhaustive validation. `src/content` resolves and validates JSON content. `src/storage` owns browser persistence. Interface components own rendering and input; facts and scoring are not embedded in components.

The validator enumerates every non-empty subset (4,095 for twelve candidates). It finds the true minimum, all optimal combinations, solvability under the configured selection limit, complete solution counts by allowed size, near-optimal complete solutions (one country larger than the minimum), attribute frequency, completion-rate denominators, per-country coverage, requirement implications, and inclusion-irreducible solutions with example routes and prunable fractions. It also distinguishes an impossible puzzle from one needing more cards than allowed. Enumeration is capped at twenty candidates. Loading rejects invalid references, duplicate IDs, invalid limits, unknown relationships, absent evidence, excluded candidates, unsolvable fixtures and a minimum inconsistent with the declared optimum. Automated content validation runs before a production build; schema/solver tests cannot independently verify factual truth, so human content review remains required.

## Identity, progress and measurement

An anonymous participant has a stable UUID independent of puzzle definitions. Each run has its own UUID, participant ID, UTC date, puzzle ID/version, catalog version, selected IDs, submitted checks and completion flag. Identity, each run and analytics use separate versioned localStorage keys. Saved check coverage is recalculated from country IDs on load rather than trusting saved scores. Invalid stored runs recover to a fresh run; completed valid runs do not restart on refresh. If browser storage is unavailable, play uses memory and displays a persistence warning. New content versions use distinct run keys; earlier saved data is retained.

Local analytics records visit, first selection, first check, each check, finish outcome and share actions, with run/date/puzzle/anonymous identifiers and a returning-player flag. Lifecycle events are deduplicated per run; the most recent 500 events are retained. Local testing can export the JSON for analysis. Nothing is sent to a server, and these local events cannot measure population-wide visitors or retention. Future server persistence and identity linking can reuse these identifiers and domain functions; neither D1 nor authoritative server enforcement is implemented now.

## Build and hosting

`npm run dev` serves local development. `npm run check` validates TypeScript, runs all automated tests and builds the static app into `dist`. `npm run build` checks TypeScript and authored content before building. The lockfile pins installed dependencies. `wrangler.jsonc` configures a static-assets Cloudflare Worker without database bindings or runtime backend code. Deployment scripts use pinned Wrangler tooling. The `quorum` Worker is connected to `paddy-devan/quorum` through Workers Builds, with `npm run check` as the build command, production branch `main`, and preview builds enabled for all other branches without exclusions. Preview URLs are enabled. These branch controls are dashboard settings, not Wrangler configuration.

Cloudflare production/preview hosting does not change the client-only game model. Accounts, social features, server analytics, a complete historical content archive, automated publication, content ingestion and competition-grade score enforcement remain outside this iteration.
